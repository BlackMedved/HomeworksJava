# AI Feedback: Архитектура HomeWork17 (ServeRest API-тесты)

Документ создан ИИ-ассистентом как обратная связь на текущую архитектуру
учебного набора API-тестов для тренировочного магазина **ServeRest** (https://serverest.dev).

## Обзор

Рассмотрены компоненты:

- `com/lesson/homework/ServeRestTest.java` — основной тестовый класс (11 тестов);
- `com/lesson/homework/models/Usuario.java` — DTO пользователя (Lombok);
- `review/ServeRestTest.java` и `review/models/Usuario.java` — ревью-вариант того же набора.

## Сильные стороны

1. **DTO вместо «сырых» JSON.** Использование `Usuario` (Lombok `@Data`) устраняет риск опечаток
   в строках, даёт compile-safe доступ к полям и типизированную сериализацию через Jackson.
2. **Устранение дублирования.** Хелперы `putUserRequest()` и `usuarioBody()` сокращают повторяющийся
   код построения запроса и тела JSON.
3. **Структурированная видимость.** `@TestMethodOrder + @Order` даёт детерминированный порядок
   и создаёт последовательный сценарий (создать → обновить → залогиниться → удалить).
4. **Именованные константы** для сообщений/статусов/пароля выносят «магические строки»
   и делают намерения заявленных тестов явными.
5. **Автоочистка данных.** Случайные email (`System.currentTimeMillis()`) позволяют не засорять
   общую БД и избегают коллизий при повторных прогонах.

## Слабые стороны и риски

1. **Хрупкость цепочки тестов.** Порядок критичен без `@Order` внутри `shouldCreateNewUser()`,
   `shouldUpdateUser()`, `shouldLogin()`, `shouldDeleteUser()`: `userId`/`token` заполняются в одном
   тесте и читаются в другом. Если JUnit выполнил тесты не по порядку — каскад падений.
   → Рекомендация: выделить lifecycle в `@Nested` классы с повторным созданием ресурсов,
   или сделать каждый тест независимым (сам регистрирует и удаляет данные).
2. **Смешанные обязанности класса.** Один класс на 11 тестов включает и юзер-кейсы, и продукт-кейсы.
   Для обучений это допустимо, для продакшена — лучше разнести по специализированным классам/пакетам
   (UsersApiTest, ProductsApiTest).
3. **Нет изоляции данных между одним и тем же email.** `userEmail` фиксирован на весь класс
   (по времени старта). Повторный прогон в рамках одной секунды может дать конфликт.
   → Мигровать на уникальный email/пользователь с datafaker (уже есть в pom).
4. **Хардкод-URL и данные в тесте.** Базовый uri и `"secret123"` зашиты. Для изучения это ок,
   но в идеале вынести в конфигурацию/`application.properties`.
5. **Отсутствие матчеров на ответы.** `shouldGetAllProducts` опирается на наличие товара
   `"Logitech MX Vertical"` — внутренняя деталь каталога. Лучше проверять invariants
   (каждый преко > 0, имя не пустое) без привязки к конкретной позиции.
6. **Статическое состояние** `baseURI` в общем классе — если будет несколько тестовых классов,
   надо следить за чисткой/областью применения (const).

## Практические замечания по коду

- `not(empty())` для проверки «имя непустое» корректнее исходного `not(notNullValue())`,
  который всегда терпел неудачу (все имена не были `null`) — это был фактический баг.
- Сериализация тела через `body(usuario)` использует Jackson, это хорошо для демонстрации DTO.
- Для строковых DTO-тел предпочтителен `text-block` с `formatted()` — он уже применён,
  и это чисто и удобочитаемо.

## Итог

Текущая архитектура — **хорошая учебная основа**: читаемая, с порядком и константами, без грубой
копипасты. Основной производственный риск — **зависимость тестов друг от друга** и привязка
к «живому» удалённому состоянию программируемого API. Рекомендации для «закрепа» и расширения:

- разнести Endpoint-группы по отдельным классам/пакетам;
- сделать тесты изолированными (self-referencing fixtures + cleanup);
- вынести настройки и ключи в конфигурацию;
- минимизировать привязку к конкретным товарам.

Оценка: **87/100** — сильная/хорошая учебная база, основной блокер — ненадёжная cross-test-зависимость и
привязка к конкретным сущностям.
