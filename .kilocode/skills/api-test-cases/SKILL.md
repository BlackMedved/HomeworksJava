# API Test Cases Skill

## Структура тест-кейса

Каждый кейс должен содержать:
- **ID** (например TC-001)
- **Название** — что именно проверяем
- **Precondition** — что должно быть готово заранее
- **Steps** — шаги воспроизведения
- **Expected result** — ожидаемый результат
- **Priority** — High/Medium/Low

## Обязательные категории проверок

1. **Happy path** — базовый успешный сценарий
2. **Валидация схемы** — обязательные поля отсутствуют, неверный тип данных, лишние поля
3. **Граничные значения** — пустая строка, максимальная длина, 0, отрицательные числа
4. **Авторизация** — без токена, просроченный токен, недостаточно прав
5. **Идемпотентность** — повторный вызов с теми же параметрами
6. **Обработка ошибок** — сервер должен возвращать понятный код/сообщение, а не молча "успех" с ошибкой внутри тела ответа

## Чего избегать

- Не пиши "проверить, что всё работает" — каждый кейс должен быть однозначно воспроизводим
- Не дублируй happy path под разными ID
